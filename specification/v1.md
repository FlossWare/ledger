# FlossWare Ledger Specification v1

**Status:** Initial specification draft  
**Specification version:** 1  
**API base path:** `/api/v1`  
**Normative language:** The terms MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are to be interpreted as normative requirements.

## 1. Abstract

Ledger defines a language-neutral, storage-independent, append-only record history. It provides portable record envelopes, append and read semantics, deterministic ordering, validation, replay, version negotiation, and import/export.

The canonical history is authoritative. Indexes, caches, projections, and materialized views are derived and rebuildable. Consuming applications retain ownership of their domain semantics and reconstructed persistent state.

This specification defines externally observable behavior. It does not prescribe an implementation language, database, physical storage format, deployment topology, or internal software architecture.

## 2. Design principles

1. **Specification authority:** This document defines the v1 contract. Implementations MUST conform to it.
2. **Append-only history:** An accepted record is immutable. The Ledger API MUST NOT provide record update or deletion operations.
3. **Portable records:** Records MUST be representable without relying on a particular programming language or database schema.
4. **Consumer ownership:** A consumer owns the interpretation of its payloads and the persistent state reconstructed from them.
5. **Storage independence:** Consumers MUST NOT need access to Ledger's physical storage representation.
6. **Rebuildability:** Derived indexes and projections MUST be reconstructible from canonical history.
7. **No broker prerequisite:** A conforming implementation MUST NOT require Kafka or another message broker.
8. **Explicit versioning:** API routes and representation media types MUST identify their versions.

## 3. Terminology

- **Ledger:** A logical append-only history managed under this specification.
- **Ledger instance:** A running implementation exposing one or more logical ledgers.
- **Namespace:** The consumer/project-defined ownership boundary for records.
- **Stream:** An ordered sequence of records within a namespace, normally representing one domain entity or logical history.
- **Record:** An immutable envelope and payload accepted into a ledger.
- **Payload:** Consumer-defined data carried by a record.
- **Position:** A Ledger-assigned, monotonically increasing ordering value within a ledger.
- **Stream sequence:** A Ledger-assigned, monotonically increasing ordering value within a stream.
- **Projection:** Derived state built by reading canonical records.
- **Replay:** Reading a defined record range in canonical order so a consumer can reconstruct or update its own state.
- **Media type:** The representation identifier used in HTTP content negotiation.

## 4. Representation and encoding

### 4.1 Canonical interchange encoding

JSON is the canonical v1 interchange encoding.

- JSON exchanged by the API MUST be UTF-8.
- JSON object member order MUST NOT carry semantic meaning.
- Consumers MUST NOT rely on insignificant whitespace.
- Integers used for positions and sequences MUST be non-negative decimal integers.
- Timestamps MUST use RFC 3339 date-time syntax and include a UTC offset. Producers SHOULD use UTC (`Z`).
- Binary payload content, when needed, MUST be encoded by the consumer within its JSON payload, for example using Base64 and an explicitly documented payload schema.

The JSON encoding is a portable representation, not a requirement that an implementation store records internally as JSON.

### 4.2 Media types

The v1 media type family is:

| Representation | Media type |
|---|---|
| Record | `application/vnd.flossware.ledger-record.v1+json` |
| Record collection | `application/vnd.flossware.ledger-records.v1+json` |
| Append request | `application/vnd.flossware.ledger-append.v1+json` |
| Append result | `application/vnd.flossware.ledger-append-result.v1+json` |
| Export document | `application/vnd.flossware.ledger-export.v1+json` |
| Error | `application/vnd.flossware.ledger-error.v1+json` |

A client MUST send an appropriate `Content-Type` for request bodies and SHOULD send an `Accept` header for the expected response representation.

A server MUST return the media type of the representation actually returned. A server MUST reject an unsupported request media type with HTTP 415 and an unacceptable response media type with HTTP 406.

The media type version identifies the representation contract. It does not replace the API route version.

## 5. Record model

### 5.1 Record envelope

A v1 record has the following logical structure:

```json
{
  "record_id": "0192f3b8-7c2a-7d31-8a4e-4b1f5f6c9a10",
  "namespace": "com.example.orders",
  "stream_id": "order/12345",
  "stream_sequence": 7,
  "position": 1042,
  "event_type": "order.payment-authorized",
  "event_version": 1,
  "occurred_at": "2026-11-05T16:20:00Z",
  "recorded_at": "2026-11-05T16:20:01Z",
  "payload": {
    "payment_reference": "pay-789",
    "amount": 42.50,
    "currency": "USD"
  },
  "metadata": {
    "correlation_id": "request-456",
    "causation_id": "record-previous"
  }
}
```

The example is illustrative. Identifiers and payload values are not reserved.

| Field | Required | Meaning |
|---|---:|---|
| `record_id` | Yes | Globally unique record identifier. UUID format is REQUIRED in v1. |
| `namespace` | Yes | Stable consumer/project ownership namespace. |
| `stream_id` | Yes | Consumer-defined logical stream identifier, unique within the namespace. |
| `stream_sequence` | Yes | One-based, contiguous sequence assigned within the stream. |
| `position` | Yes | One-based, contiguous position assigned within the logical ledger. |
| `event_type` | Yes | Stable consumer-defined event type identifier. |
| `event_version` | Yes | Positive integer identifying the payload schema version for this event type. |
| `occurred_at` | Yes | Time the consumer says the event occurred. |
| `recorded_at` | Yes | Time the Ledger accepted the record. Assigned by the Ledger. |
| `payload` | Yes | Consumer-defined JSON value. |
| `metadata` | No | Optional consumer-defined JSON object for cross-cutting context. Defaults to an empty object in returned records. |
| `origin` | No | Ledger-managed provenance for imported records, including source ledger identity and source ordering values. Absent for records first appended to this ledger. |

### 5.2 Identity

`record_id` MUST uniquely identify a record across imports and exports. A record ID MUST NOT be reused for different record content.

A client SHOULD generate a UUID before append so it can safely retry an uncertain request. The Ledger MUST treat a repeated append of the same record ID and identical immutable content as an idempotent retry. Reuse of a record ID with different immutable content MUST fail with HTTP 409.

### 5.3 Namespace and stream identity

`namespace` and `stream_id` are opaque, case-sensitive UTF-8 strings. Implementations MUST NOT infer domain semantics from them.

The pair (`namespace`, `stream_id`) identifies a stream within a logical ledger. A consumer SHOULD use stable identifiers and MUST NOT encode database-specific primary-key assumptions into the Ledger contract.

### 5.4 Event identity and payload

`event_type` is a stable consumer-defined identifier. `event_version` identifies the schema of the payload for that event type. It is not the Ledger specification version.

Ledger MUST preserve payload values without domain-specific rewriting. Ledger MAY validate a payload against a consumer-supplied schema when that capability is explicitly configured. Such validation MUST NOT change the stored payload.

### 5.5 Timestamps

`occurred_at` is producer-supplied and MUST be preserved exactly as a valid RFC 3339 timestamp value.

`recorded_at` is assigned by the Ledger at acceptance time. Clients MUST NOT assign or override it during a normal append. During import, source recording time MUST be preserved in the record's `origin` provenance while the destination's `recorded_at` is assigned as the destination acceptance time.

Timestamps MUST NOT be used as the canonical ordering mechanism. Ledger positions define ordering.

### 5.6 Imported-record provenance

The optional `origin` field is reserved for Ledger-managed import provenance. When present, it MUST be an object containing:

- `source_ledger_id`: identifier of the ledger from which the record was exported.
- `source_position`: the record's position in that source ledger.
- `source_stream_sequence`: the record's sequence in its source stream.
- `source_recorded_at`: the source ledger's original recording timestamp.

A client MUST NOT set or modify `origin` during normal append. Import MUST populate it from the export document's source context. If an imported record already has origin provenance, the importer MUST preserve that provenance and MUST NOT overwrite it with the immediate source ledger's identity. The export document itself supplies the immediate source ledger identity and ordering values for the current transfer.

### 5.7 Assigned fields

For normal append requests, clients supply `record_id`, `namespace`, `stream_id`, `event_type`, `event_version`, `occurred_at`, `payload`, and optional `metadata`.

The Ledger assigns `stream_sequence`, `position`, and `recorded_at`. Clients MUST NOT set these fields on normal append requests. Import is governed separately by Section 11.

## 6. Append semantics

### 6.1 Append operation

An append MUST be atomic for each record. A record is either accepted in full or not accepted.

On acceptance, the Ledger MUST:

1. Validate the request representation and required envelope fields.
2. Enforce record ID uniqueness and idempotency rules.
3. Assign the next ledger position.
4. Assign the next sequence within the specified stream.
5. Assign `recorded_at`.
6. Persist the immutable record in canonical history.
7. Return the accepted record or its complete assigned identity and ordering information.

The append response MUST NOT report success before the record is durably accepted according to the implementation's documented durability guarantees.

### 6.2 Ordering

Positions MUST be strictly increasing and contiguous within a logical ledger. Stream sequences MUST be strictly increasing and contiguous within a stream.

The Ledger MUST serialize conflicting appends sufficiently to ensure that no two distinct accepted records receive the same position or the same stream sequence.

A ledger position defines total order within that ledger. A stream sequence defines order within its stream. Wall-clock timestamps do not override either order.

### 6.3 Concurrency control

An append request MAY include an expected stream sequence. When supplied, the Ledger MUST accept the append only if the current stream sequence matches the expected value. A mismatch MUST return HTTP 409 and MUST NOT append the record.

This provides optimistic concurrency without requiring a broker or distributed coordination service.

### 6.4 Batch append

A v1 implementation MAY support batch append. If supported, the batch MUST be atomic: either all new records are accepted in the batch or none are.

Within a batch, records MUST receive ledger positions in request order. Stream sequences MUST be assigned in request order for each stream. An implementation that does not support atomic batch append MUST reject the batch operation rather than silently process it partially.

### 6.5 Immutability

The public contract MUST NOT expose update or delete operations for accepted records. Corrections are represented by appending a new compensating or superseding event defined by the consumer's domain.

## 7. Read semantics

A conforming implementation MUST support:

- Retrieve a record by `record_id`.
- Retrieve records for a namespace and stream in ascending stream sequence.
- Retrieve records from a ledger position, in ascending ledger position.
- Paginate collection results.

A read MUST return the original accepted record content and its assigned ordering fields.

Pagination MUST use an opaque continuation token or an equivalent stable cursor. Clients MUST treat continuation tokens as opaque. A continuation token MUST bind to the relevant query scope and ordering so that it cannot silently change the meaning of a page sequence.

A read response MUST identify whether more records are available and provide a continuation token when another page exists.

## 8. Replay

Replay is an ordered read of canonical records, not a separate source of truth.

A replay request MUST identify its scope using either:

- a namespace and stream, ordered by stream sequence; or
- a ledger position range, ordered by ledger position.

The replay response MUST preserve the selected canonical ordering and MUST expose the record positions/sequences needed to resume.

Replay MUST NOT mutate canonical history. A consumer applies records to its own reducer, projection, or persistence layer.

A consumer that needs exactly-once effects in its own database MUST coordinate its projection update and replay checkpoint transactionally within that consumer's persistence boundary. Ledger does not claim to provide distributed exactly-once transactions across independent systems.

## 9. Validation

A conforming implementation MUST validate:

- Supported API and media type versions.
- Required envelope fields and field types.
- UUID syntax and record ID uniqueness.
- Non-empty namespace, stream ID, and event type.
- Positive event version.
- Valid RFC 3339 timestamps.
- JSON validity of payload and metadata.
- Ledger and stream ordering constraints.
- Append-only and idempotency constraints.

A validation failure MUST return a structured error and MUST NOT partially append a record.

Domain payload schema validation is optional and consumer-defined. An implementation MUST distinguish envelope validation failures from consumer payload schema failures.

## 10. HTTP API

All v1 endpoints are rooted at `/api/v1/`.

### 10.1 Append a record

`POST /api/v1/records`

Request: `application/vnd.flossware.ledger-append.v1+json`

Example:

```json
{
  "record_id": "0192f3b8-7c2a-7d31-8a4e-4b1f5f6c9a10",
  "namespace": "com.example.orders",
  "stream_id": "order/12345",
  "event_type": "order.payment-authorized",
  "event_version": 1,
  "occurred_at": "2026-11-05T16:20:00Z",
  "payload": {
    "payment_reference": "pay-789",
    "amount": 42.50,
    "currency": "USD"
  },
  "metadata": {
    "correlation_id": "request-456"
  },
  "expected_stream_sequence": 6
}
```

Success: HTTP 201 for a newly accepted record, with an append-result representation containing the accepted record identity and assigned ordering fields. An identical idempotent retry MAY return HTTP 200 and MUST identify that the record already existed.

### 10.2 Retrieve a record

`GET /api/v1/records/{record_id}`

Success: HTTP 200 with a record representation. Unknown record IDs return HTTP 404.

### 10.3 Read a stream

`GET /api/v1/records?namespace={namespace}&stream_id={stream_id}`

Namespace and stream identifiers are query parameters rather than path segments so that opaque identifiers may safely contain characters such as slashes. Clients MUST percent-encode query parameter values as UTF-8. Supported query parameters:

- `after_sequence`: return records with stream sequence greater than this value.
- `through_sequence`: optional inclusive upper bound.
- `limit`: maximum records in the page, subject to a server-defined maximum.
- `cursor`: opaque continuation token returned by a previous page.

Results MUST be ordered by ascending stream sequence.

### 10.4 Read by ledger position

`GET /api/v1/records?after_position={n}&through_position={n}&limit={n}&cursor={token}`

Results MUST be ordered by ascending ledger position.

### 10.5 Export

`GET /api/v1/export`

The export operation returns a portable export document. Implementations MUST support exporting a complete logical ledger or a clearly identified subset by namespace, stream, or position range.

### 10.6 Import

`POST /api/v1/import`

The import operation accepts a v1 export document. Import MUST validate the entire document before making it visible as accepted history. The implementation MUST document whether import targets an empty ledger or supports merging into an existing ledger. Import behavior MUST preserve source record identity and source ordering metadata and MUST be safe to retry.

### 10.7 Replay

Replay uses the same read scope and ordering rules as Section 8. Implementations MAY expose replay as a dedicated endpoint or use the stream and position read endpoints as the replay interface. A dedicated endpoint MUST NOT introduce different ordering or mutation semantics.

## 11. Import and export format

An export document uses `application/vnd.flossware.ledger-export.v1+json` and has this logical structure:

```json
{
  "format": "flossware-ledger-export",
  "format_version": 1,
  "source_ledger_id": "ledger-instance-identifier",
  "exported_at": "2026-11-05T16:30:00Z",
  "scope": {
    "type": "ledger"
  },
  "records": [
    {
      "record_id": "0192f3b8-7c2a-7d31-8a4e-4b1f5f6c9a10",
      "namespace": "com.example.orders",
      "stream_id": "order/12345",
      "stream_sequence": 7,
      "position": 1042,
      "event_type": "order.payment-authorized",
      "event_version": 1,
      "occurred_at": "2026-11-05T16:20:00Z",
      "recorded_at": "2026-11-05T16:20:01Z",
      "payload": {
        "payment_reference": "pay-789"
      },
      "metadata": {}
    }
  ]
}
```

An export MUST declare its format and format version, source ledger identity, export time, scope, and records.

An export MUST preserve record IDs, envelope fields, payloads, metadata, any existing `origin` provenance, and the exported ledger's source ordering values. Records MUST be ordered by source ledger position when exporting a ledger-position scope. A stream-scoped export MUST be ordered by source stream sequence.

When importing records from another ledger, the destination MUST assign destination-local positions and stream sequences according to the destination's append order. It MUST preserve the source ledger ID, source position, source stream sequence, and source recording time in the record's `origin` provenance. It MUST NOT misrepresent source positions as destination positions. Re-export MUST retain this provenance.

An import implementation MUST reject conflicting record IDs whose immutable content differs. Re-importing identical records MUST NOT create duplicates.

## 12. Error representation

Errors use `application/vnd.flossware.ledger-error.v1+json`.

```json
{
  "error": {
    "code": "record_id_conflict",
    "message": "The record ID already exists with different content.",
    "details": {
      "record_id": "0192f3b8-7c2a-7d31-8a4e-4b1f5f6c9a10"
    }
  }
}
```

The `code` is a stable machine-readable identifier. The `message` is human-readable and MUST NOT be used for programmatic branching. `details` is optional structured context.

Implementations MUST use appropriate HTTP status codes:

| Status | Meaning |
|---:|---|
| 200 | Successful read or idempotent retry |
| 201 | New record accepted |
| 400 | Malformed request or invalid field |
| 404 | Record or requested resource not found |
| 409 | Record ID conflict or optimistic concurrency conflict |
| 406 | Requested response media type is not supported |
| 409 | Unsupported state transition or import conflict |
| 413 | Request or export exceeds configured limits |
| 415 | Request media type is not supported |
| 422 | Syntactically valid request fails semantic validation |
| 500 | Unexpected server failure |

An implementation MAY define additional stable error codes, but MUST preserve the status and error envelope semantics above.

## 13. Integrity and durability

Accepted records MUST remain retrievable and unchanged for the retention lifetime declared by the implementation. A conforming implementation MUST document its durability and backup assumptions.

The v1 specification does not mandate a hash-chain algorithm, cryptographic signature scheme, replication protocol, or physical backup mechanism. Implementations MAY provide additional integrity verification, but such extensions MUST NOT alter record identity, canonical ordering, or portability.

## 14. Security and privacy

Authentication, authorization, encryption at rest, and transport security are deployment concerns and are not prescribed by the v1 wire contract. Implementations exposed beyond a trusted local process SHOULD use authenticated transport and enforce namespace-level access controls.

Implementations MUST NOT treat namespace or stream identifiers as authorization credentials.

Payloads and metadata may contain sensitive consumer data. Implementations SHOULD support operational controls appropriate to the deployment, including access restriction, backup protection, and documented retention.

## 15. Compatibility and versioning

The v1 API path is `/api/v1/`. The v1 media types are defined in Section 4.2.

A v1 implementation MUST NOT silently reinterpret an existing field or change the meaning of an existing operation.

Non-breaking additions MAY be made within v1 when they preserve the behavior of existing conforming clients. A change is breaking if it removes or changes a required field, changes ordering or append semantics, changes an existing field's meaning or type, changes an endpoint's established behavior, or makes a previously valid v1 interaction invalid.

A breaking change requires a new cohesive specification version and corresponding API/media type version, for example v2. A patch release of documentation does not create a new protocol version.

Implementations MUST identify the specification version they implement in their published documentation and SHOULD expose it through a service capabilities endpoint in a future-compatible manner.

## 16. Conformance

An implementation conforms to Ledger v1 only if it satisfies all REQUIRED and MUST requirements in this specification.

At minimum, conformance testing MUST verify:

1. Record envelope validation.
2. Unique record identity and idempotent retry behavior.
3. Conflict detection for reused record IDs with different content.
4. Append-only behavior.
5. Contiguous ledger positions and per-stream sequences.
6. Optimistic concurrency behavior when expected sequence is supplied.
7. Ordered stream and ledger reads.
8. Stable pagination and replay continuation.
9. Export/import round-trip preservation.
10. Safe repeat import behavior.
11. Rejection of unsupported media types and API versions.
12. No dependency on consumer database schemas or physical Ledger storage.

## 17. Deferred topics

The following are intentionally outside the initial v1 contract unless later incorporated through a specification revision:

- Multi-writer distributed consensus and replication.
- Cross-ledger transactions.
- Cryptographic hash chains and signatures.
- Snapshot formats and snapshot-assisted replay.
- Event transformation/upcasting frameworks.
- Schema registry service.
- Streaming subscriptions and push delivery.
- Broker integration.
- Retention deletion and compaction semantics.
- Compression and binary interchange formats.
- Authorization protocol and identity federation.

These are not implicit requirements. An implementation MUST NOT require them to claim basic v1 conformance.
